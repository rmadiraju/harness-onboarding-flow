02 Testing Philosophy

Core Principle

Test the real thing. No mocks at E2E level. Every run starts with cleanup, stages are observable, failures are gated. Pipelines are modular and composable via an orchestrator.

LayerWhat We TestTool
UIOnboarding form, navigation, add-service, release UIPlaywright
APIOnboarding, status polling, provisioningPython (requests)
GitRepo creation, code push, PR/merge triggersPython (subprocess/GitPython)
HarnessPipeline existence, trigger validation, executionPython (Harness API)
AWSRDS, S3, DynamoDB, ECS/EKS, accountsPython (boto3)
DeployHealth checks, version validation, all envsPython (requests)

03 Test Data Strategy

test_project:
  name: "e2e-test-project-001"
  resources: [microservice, rds, s3, dynamodb]

All artifacts use e2e-test-* namespace. AWS resources tagged Environment: e2e-test. Never shared with manual testing.

Cleanup-First Pattern

Every run begins by tearing down previous artifacts. No stale state, same data reusable, partial failures don't block.

04 Orchestrator Pipeline Architecture

Instead of one monolithic pipeline, the suite is independent, modular pipelines — each a complete test scenario. A single Orchestrator Pipeline selects which child pipelines to run via Harness Input Sets.

Why This Pattern?

Run onboarding-only for onboarding changes. Day-2 only for CI/CD changes. Everything for nightly regression. Add new scenarios without touching existing pipelines.

Orchestrator — "Run E2E Suite"
🎛 E2E Orchestrator Pipeline
Input: select which test pipelines to run · Configurable via Harness Input Sets
▼ triggers selected pipelines ▼
Pipeline 1: Onboarding E2E
Setup → UI Onboard → Validate → Deploy → STG → PROD
Pipeline 2: Day-2 CI/CD E2E
Setup → Update Code → Deploy → STG → PROD
+ extensible
Pipeline 3: Add Service
Pipeline 4: Rollback
Pipeline N: Custom

Orchestrator Configuration

YAML — Harnesspipeline:
  name: "E2E Test Suite Orchestrator"
  identifier: e2e_orchestrator
  stages:
    - stage:
        name: "Run Onboarding E2E"
        type: Pipeline
        spec:
          org: platform_team
          pipeline: e2e_onboarding_pipeline
        when:
          condition: "<+pipeline.variables.run_onboarding>" == "true"
    - stage:
        name: "Run Day-2 CI/CD E2E"
        type: Pipeline
        spec:
          org: platform_team
          pipeline: e2e_day2_cicd_pipeline
        when:
          condition: "<+pipeline.variables.run_day2_cicd>" == "true"
  variables:
    - name: run_onboarding
      type: String
      default: "true"
    - name: run_day2_cicd
      type: String
      default: "true"

07 Language Strategy

Recommendation

Playwright (TS) for UI + Python for everything else. All-Playwright is possible but painful for git, AWS, and polling.

TaskPlaywrightPythonVerdict
UI InteractionsExcellentPossible (bindings)→ Playwright
Git OperationsAwkward (child_process)Natural→ Python
REST API CallsGood (fetch)Excellent→ Python
AWS ValidationPossible (JS SDK)Excellent (boto3)→ Python
Polling/WaitingTimeout conflictsSimple→ Python

Why not all-Playwright? Timeout hell (30s default vs 15min AWS polling), poor error context (stderr vs boto3 ClientError), dependency bloat (~2GB image).

Python-Only Teams

Playwright has Python bindings — viable single-language option, but TS bindings have better docs and faster updates.

08 Docker Containerization

Verdict: Yes, use Docker. Two lean images.

Reproducibility, isolation, native Harness CI support. Don't run on bare delegates.

┌───────────────────────────┐  ┌────────────────────────────────┐
│  e2e-playwright:latest     │  │  e2e-python:latest             │
│  ────────────────────────  │  │  ────────────────────────────  │
│  Base: playwright:v1.40.0  │  │  Base: python:3.11-slim        │
│  Node.js 20, Chromium      │  │  boto3, requests, pytest       │
│  Test specs (TS)           │  │  GitPython, pyyaml, AWS CLI    │
│  Size: ~1.2 GB             │  │  git, curl, jq                 │
│  → UI stages               │  │  Size: ~450 MB                 │
└───────────────────────────┘  │  → All non-UI stages            │
                               └────────────────────────────────┘
⚠ Do NOT combine into one ~2GB image.

09 Failure Handling

CategoryExampleResponse
Infra FlakeAWS provisioning timeoutAuto-retry (max 1)
True RegressionOnboarding API 500Fail, alert team
Test BugUI selector changedFail, fix test
Env IssueDelegate downFail, alert infra

Every stage produces: screenshots, API responses, pipeline execution IDs, AWS ARNs, Git SHAs, timestamps.

Conditional Cleanup

SUCCESS → full teardown. FAILURE → resources preserved for debugging. Manual: make e2e-cleanup.

13 Implementation Roadmap

PHASE 1 — FOUNDATION
Cleanup, API Onboarding, Provisioning Poll
Build Setup stage, cleanup scripts (Git, AWS, Platform API), provisioning poller. Establish the two Docker images.
PHASE 2 — ARTIFACT VERIFICATION
Git Repo, Pipelines, AWS Resource Validation
Build Validate Artifacts stage. Python scripts for repo structure, Harness pipeline checks, boto3 resource verification.
PHASE 3 — DEPLOYMENT VALIDATION
Deploy to DEV/TEST, Health Checks
Build Deploy stage. Trigger pipelines via Harness API, poll completion, validate hello-world across environments.
PHASE 4 — RELEASE VALIDATION
Release to STG & PROD, Approval Gates
Build Release stages. Complete Pipeline 1 (Onboarding E2E). Auto-approve gates, multi-env health checks.
PHASE 5 — DAY-2 CI/CD PIPELINE
Code Push, PR/Merge, Full CI/CD Loop
Build Pipeline 2. Git operations, PR creation/merge, validate triggers and full deployment cycle.
PHASE 6 — UI AUTOMATION
Playwright Onboarding + Release Flows
Implement Playwright tests for onboarding form, release UI, add-service flow. Screenshots, error states.
PHASE 7 — ORCHESTRATOR & REPORTING
Meta Pipeline, Reports, Notifications
Build orchestrator with configurable input sets. HTML reports, Slack alerts, retry logic, flake elimination.
