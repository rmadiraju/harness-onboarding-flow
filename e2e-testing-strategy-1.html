02 Testing Philosophy & Principles

Core Philosophy

Test the real thing. No mocks at the E2E level. Every run starts with cleanup, every stage is observable, and failures are stage-gated so we don't waste time downstream.

PrincipleWhat It Means
Test the Real ThingUse actual UI, real APIs, real Git repos, real AWS resources
Idempotent & RepeatableEvery run starts with cleanup — same data, deterministic outcomes
ObservableEvery stage produces logs, screenshots, API responses, status artifacts
Stage-GatedFailure in Stage 2 stops execution — no wasted time in Stage 5
Parallel When SafeIndependent checks (S3, DynamoDB) run in parallel; sequential deploys remain serial

test_project:

  resources: [microservice, rds, s3, dynamodb]

Isolation Rules

All test artifacts use a dedicated namespace (e2e-test-*) so cleanup is targeted and safe. AWS resources are tagged with Environment: e2e-test. Git repos follow a naming convention like e2e-test-project-*. Test data is never shared with manual or exploratory testing.

Cleanup-First Pattern

Every E2E run begins by tearing down artifacts from the previous run. This ensures no stale state, enables data reuse, and prevents partial failures from blocking the next run.

Stage 1: Cleanup & Reset

Destroy all artifacts from previous runs. The goal is a clean slate before every execution.

StepActionMethod
1.1Delete test Git repoGitHub API — DELETE /repos/{org}/{repo}
1.2Delete Harness pipelinesHarness API — delete e2e-test-*
1.3Tear down AWS resourcesboto3 — delete resources tagged e2e-test
1.4Clean AWS accounts / org unitsAWS Organizations API
1.5Remove test project from platform DBAdmin API — DELETE /admin/projects/{id}
1.6Wait for async cleanupPoll status / CloudFormation
Error Handling

If cleanup fails: retry once, then fail the entire pipeline. Never proceed with stale state. All operations should be idempotent — "not found" is a valid success.

Bash# Example: Git repo cleanup
RESPONSE=$(curl -s -o /dev/null -w "%{http_code}" \
  -X DELETE -H "Authorization: token ${GIT_TOKEN}" \
  "https://api.github.com/repos/${ORG}/${E2E_REPO_NAME}")

if [[ "$RESPONSE" == "204" || "$RESPONSE" == "404" ]]; then
  echo "✅ Git repo cleanup: OK"
else
  echo "❌ Git repo cleanup failed: HTTP $RESPONSE" && exit 1
fi

Stage 3: Provisioning Wait & Verify

Poll the platform's status API with exponential backoff until provisioning completes or times out (15 min).

Pythonimport time, requests, sys, os

TIMEOUT, INTERVAL = 900, 30
start = time.time()
while time.time() - start < TIMEOUT:
    resp = requests.get(f"{API}/onboard/status/{REQUEST_ID}",
                        headers={"Authorization": f"Bearer {TOKEN}"})
    status = resp.json().get("status")
    if status == "COMPLETED":
        print("✅ Provisioning complete!")
        sys.exit(0)
    elif status == "FAILED":
        print(f"❌ FAILED: {resp.json().get('error')}")
        sys.exit(1)
    time.sleep(INTERVAL)
print("❌ TIMEOUT")
sys.exit(1)

import boto3, time, requests, os

def wait_for_additional_provisioning(request_id, timeout=600):
    """Poll until the additional service is provisioned."""
    api = os.environ["PLATFORM_API"]
    token = os.environ["PLATFORM_TOKEN"]
    start = time.time()
    while time.time() - start < timeout:
        resp = requests.get(
            f"{api}/services/status/{request_id}",
            headers={"Authorization": f"Bearer {token}"}
        )
        status = resp.json().get("status")
        if status == "COMPLETED":
            return resp.json()
        elif status == "FAILED":
            raise Exception(f"Additional service provisioning failed: {resp.json()}")
        time.sleep(20)
    raise TimeoutError("Additional service provisioning timed out")

def verify_new_dynamodb_table(session, table_name):
    """Verify the newly added DynamoDB table exists and is configured."""
    dynamodb = session.client('dynamodb')
    resp = dynamodb.describe_table(TableName=table_name)
    table = resp['Table']
    assert table['TableStatus'] == 'ACTIVE', f"Table status: {table['TableStatus']}"
    
    # Verify key schema
    keys = {k['AttributeName']: k['KeyType'] for k in table['KeySchema']}
    assert 'orderId' in keys, "Partition key 'orderId' not found"
    print(f"✅ DynamoDB table {table_name} is ACTIVE with correct schema")

def verify_existing_resources_unaffected(session, project_config):
    """Ensure adding a service didn't break existing resources."""
    # Check RDS still available
    rds = session.client('rds')
    resp = rds.describe_db_instances(DBInstanceIdentifier=project_config['rds_id'])
    assert resp['DBInstances'][0]['DBInstanceStatus'] == 'available'
    print("✅ Existing RDS still available")
    
    # Check S3 still accessible
    s3 = session.client('s3')
    s3.head_bucket(Bucket=project_config['s3_bucket'])
    print("✅ Existing S3 bucket still accessible")
    
    # Check original DynamoDB table
    dynamodb = session.client('dynamodb')
    resp = dynamodb.describe_table(TableName=project_config['dynamodb_table'])
    assert resp['Table']['TableStatus'] == 'ACTIVE'
    print("✅ Existing DynamoDB table still ACTIVE")

import subprocess, os, json, tempfile, requests

GIT_TOKEN = os.environ["GIT_TOKEN"]
ORG = os.environ["ORG"]
REPO = os.environ["E2E_REPO_NAME"]

def clone_and_branch(repo_url, branch_name):
    """Clone repo and create feature branch."""
    work_dir = tempfile.mkdtemp(prefix="e2e-day2-")
    subprocess.run(["git", "clone", repo_url, work_dir], check=True)
    subprocess.run(["git", "checkout", "-b", branch_name], cwd=work_dir, check=True)
    return work_dir

def add_orders_endpoint(work_dir):
    """Add a new /orders endpoint that uses DynamoDB."""
    # Read existing app file
    app_file = os.path.join(work_dir, "src", "app.py")  # or app.js, etc.
    with open(app_file, "r") as f:
        content = f.read()
    
    # Append new endpoint
    new_code = '''

# --- E2E Day-2 Test: Orders Endpoint ---
@app.route('/orders', methods=['GET'])
def get_orders():
    dynamodb = boto3.resource('dynamodb')
    table = dynamodb.Table(os.environ.get('ORDERS_TABLE', 'e2e-orders-table'))
    response = table.scan(Limit=10)
    return jsonify({"orders": response.get('Items', []), "status": "ok"})
'''
    with open(app_file, "w") as f:
        f.write(content + new_code)
    
    # Update config
    config_file = os.path.join(work_dir, "config", "env.json")
    if os.path.exists(config_file):
        with open(config_file, "r") as f:
            config = json.load(f)
        config["ORDERS_TABLE"] = "e2e-orders-table"
        with open(config_file, "w") as f:
            json.dump(config, f, indent=2)

def commit_and_push(work_dir, branch_name):
    """Commit changes and push to remote."""
    subprocess.run(["git", "add", "."], cwd=work_dir, check=True)
    subprocess.run(
        ["git", "commit", "-m", "feat: add orders endpoint using DynamoDB [e2e-day2]"],
        cwd=work_dir, check=True
    )
    subprocess.run(
        ["git", "push", "origin", branch_name],
        cwd=work_dir, check=True
    )

def create_and_merge_pr(branch_name):
    """Create PR via GitHub API, wait for CI, then merge."""
    headers = {"Authorization": f"token {GIT_TOKEN}"}
    
    # Create PR
    pr_resp = requests.post(
        f"https://api.github.com/repos/{ORG}/{REPO}/pulls",
        headers=headers,
        json={
            "title": "feat: add orders endpoint [e2e-day2]",
            "head": branch_name,
            "base": "main",
            "body": "Automated E2E Day-2 test — adds /orders endpoint"
        }
    )
    pr_number = pr_resp.json()["number"]
    print(f"✅ PR #{pr_number} created")
    
    # ... wait for PR pipeline (see Stage 6 polling logic) ...
    
    # Merge PR
    merge_resp = requests.put(
        f"https://api.github.com/repos/{ORG}/{REPO}/pulls/{pr_number}/merge",
        headers=headers,
        json={"merge_method": "squash"}
    )
    assert merge_resp.status_code == 200, f"Merge failed: {merge_resp.text}"
    print(f"✅ PR #{pr_number} merged to main")

def validate_full_cicd(harness_api, api_key, main_pipeline_id, commit_sha):
    """Wait for main pipeline, then validate deployment has the right version."""
    
    # Wait for main pipeline execution triggered by merge
    execution = poll_for_new_execution(
        harness_api, api_key, main_pipeline_id,
        timeout=120, status_filter="Running"
    )
    print(f"✅ Main pipeline triggered: {execution['uuid']}")
    
    # Wait for pipeline to complete
    final_status = poll_execution_status(
        harness_api, api_key, execution['uuid'], timeout=600
    )
    assert final_status == "SUCCESS", f"Pipeline failed: {final_status}"
    print("✅ Main pipeline completed successfully")
    
    # Validate deployed version matches our commit
    for env in ["dev", "test"]:
        resp = requests.get(
            f"https://e2e-test-project-001.{env}.internal.company.com/version"
        )
        deployed_sha = resp.json().get("commit", resp.json().get("version"))
        assert commit_sha[:8] in str(deployed_sha), \
            f"Version mismatch in {env}: expected {commit_sha[:8]}, got {deployed_sha}"
        print(f"✅ {env}: deployed version matches commit {commit_sha[:8]}")

import boto3, requests

def validate_orders_endpoint(app_base_url, dynamodb_session):
    """Seed data, hit the app, verify it reads from DynamoDB."""
    
    # 1. Seed test data
    table = dynamodb_session.resource('dynamodb').Table('e2e-orders-table')
    table.put_item(Item={
        'orderId': 'e2e-order-001',
        'product': 'E2E Test Widget',
        'quantity': 1,
        'status': 'confirmed'
    })
    print("✅ Seeded test order into DynamoDB")
    
    # 2. Hit the new endpoint
    resp = requests.get(f"{app_base_url}/orders", timeout=10)
    assert resp.status_code == 200, f"Orders endpoint returned {resp.status_code}"
    orders = resp.json().get("orders", [])
    assert any(o['orderId'] == 'e2e-order-001' for o in orders), \
        "Seeded order not found in response"
    print("✅ /orders endpoint returns seeded data from DynamoDB")
    
    # 3. Verify original health endpoint still works
    health = requests.get(f"{app_base_url}/health", timeout=10)
    assert health.status_code == 200, "Health check failed after code change!"
    print("✅ /health endpoint still healthy (no regression)")
    
    # 4. Cleanup test data
    table.delete_item(Key={'orderId': 'e2e-order-001'})
    print("✅ Cleaned up test data")

Add Service (UI) → Verify resource provisioned → Push code change (Git) → PR pipeline passes → Merge → Main pipeline deploys → Validate app uses new resource (HTTP + AWS SDK). This proves the platform is a real, usable development environment.

08 Language Strategy: Playwright + Python Hybrid

Decision Summary

Recommended: Playwright (TypeScript) for UI + Python for everything else. This is a deliberate split, not a compromise. Each tool handles what it's best at. Trying to do everything in Playwright is possible but creates unnecessary pain.

Can You Do Everything in Playwright?

Technically, yes. Playwright can execute shell commands via Node.js child_process, make HTTP requests via fetch, and even interact with AWS using the JS SDK. But just because you can doesn't mean you should. Here's the honest breakdown:

TaskPlaywright (TS/JS)PythonVerdict
UI Interactions
Form fills, clicks, navigation, screenshots		 Excellent — this is its entire purpose Possible (Playwright has Python bindings) but TS is the first-class citizen → Playwright
Git Operations
Clone, branch, modify files, commit, push		 Awkward — requires child_process.exec('git clone ...'), string interpolation, error handling is clunky Natural — subprocess.run() + native file I/O, GitPython library available → Python
File Modification
Read/write source code, update configs		 Possible via fs module but verbose for JSON/YAML manipulation Natural — json.load/dump, pathlib, pyyaml → Python
REST API Calls
Harness API, GitHub API, Platform API		 Good with fetch / axios Excellent — requests library is extremely clean → Python (simpler syntax, better for polling loops)
AWS Resource Validation
boto3 for RDS, S3, DynamoDB, ECS checks		 Possible via AWS JS SDK, but less documented for infrastructure automation Excellent — boto3 is the gold standard for AWS automation → Python
Polling & Waiting
Status checks with backoff and timeout		 Async/await works but Playwright test timeouts can interfere Simple — time.sleep() + loops, no event loop complexity → Python

Why Not All-Playwright? The Real Problems

Problem 1: Test Timeout Hell

Playwright tests have default timeouts (30s per action, 5min per test). When you're polling AWS provisioning for 15 minutes or waiting for a Harness pipeline to complete, you're fighting the framework instead of using it. You'd need to set absurdly high timeouts, losing the benefit of Playwright's timeout safety net for actual UI tests.

Problem 2: Error Context

When a Python boto3 call fails, you get a clear ClientError with the AWS error code. When a child_process.exec('aws dynamodb describe-table ...') fails inside Playwright, you get a string of stderr output that you have to parse yourself. Debugging is significantly harder.

Problem 3: Dependency Bloat

Your Playwright container needs Node.js + browsers + Chromium. Adding the AWS JS SDK, git tools, and all infrastructure libraries makes the image huge and fragile. Better to have a lean Playwright image for UI and a lean Python image for infra.

How They Communicate

Playwright stages and Python stages are separate steps in the same Harness pipeline. Data flows between them via Harness pipeline variables and output variables:

YAML — Harness Pipeline# Playwright step outputs → Python step inputs
- step:
    name: "UI Onboarding"
    type: Run
    spec:
      connectorRef: e2e_docker_connector
      image: e2e-playwright:latest
      shell: Sh
      command: |
        npx playwright test onboarding.spec.ts
        # Write outputs for downstream steps
        echo "REQUEST_ID=$(cat artifacts/request-id.txt)" >> $HARNESS_OUTPUT
      outputVariables:
        - name: REQUEST_ID

- step:
    name: "Poll Provisioning"
    type: Run
    spec:
      connectorRef: e2e_docker_connector
      image: e2e-python:latest
      shell: Sh
      command: |
        # Read from previous step
        python3 scripts/poll_provisioning.py \
          --request-id "<+steps.UI_Onboarding.output.outputVariables.REQUEST_ID>"
      envVariables:
        REQUEST_ID: "<+steps.UI_Onboarding.output.outputVariables.REQUEST_ID>"

What About Playwright Python Bindings?

Playwright offers Python bindings (playwright-python). You could write everything in Python using these. However, the TypeScript bindings are the primary/first-class implementation — better docs, faster updates, and the auto-wait/selector engine is more battle-tested. If your team is Python-only and strongly prefers it, Playwright-Python is a viable option but expect slightly lagging documentation and community support.

Decision Criteria

If your team has strong TypeScript skills → Playwright TS + Python (recommended).
If your team is Python-only → Playwright Python + Python (viable, single language, slight tradeoff on Playwright ecosystem).
If you insist on all-Playwright-TS → Expect pain on git ops, AWS, and polling. Not recommended.

09 Docker Containerization: Analysis & Recommendation

Verdict: Yes, Use Docker. But smartly.

Dockerizing your E2E tests is the right call for Harness pipelines, but you don't need a single monolithic container. Use two purpose-built images and lean on Harness's native step orchestration.

Why Docker Is the Right Choice

BenefitWhy It Matters for E2E
ReproducibilityPlaywright needs specific browser binaries (Chromium, Firefox). Python needs specific boto3/requests versions. Docker guarantees the exact same environment every run — no "works on the delegate but not in CI" issues.
IsolationE2E tests touch real AWS accounts and Git repos. Running in a container provides a clean, isolated filesystem. No leftover git credentials, no stale AWS token caches.
Harness CompatibilityHarness CI Run steps natively support Docker images. Your steps just reference image: your-registry/e2e-tests:latest and everything works. No delegate plugin installation needed.
PortabilitySame images can run locally for debugging (docker run -it e2e-python bash), in Harness CI, in GitHub Actions, or in any other CI system. No vendor lock-in on the test execution.
Version PinningPin Playwright version, browser version, Python packages, AWS CLI version. No surprises when a delegate gets patched.

Why Not Run Directly on the Harness Delegate?

ApproachProblem
Shell scripts on delegateDelegate may not have Python 3.11, boto3, Playwright, or correct browser binaries. Installing at runtime wastes 2-5 min per run and is fragile.
Pre-configured delegateCouples your tests to a specific delegate version. Delegate upgrades can break your tests. Multiple teams sharing delegates means dependency conflicts.
Harness Cloud (hosted)Good option if available, but you lose control over installed tools and versions. Heavy dependencies like Playwright + Chromium may not be pre-installed.

Recommended: Two Docker Images

When Docker Is NOT Required

There are cases where containerization adds overhead without enough benefit:

ScenarioAlternative

Docker containers are the right choice for this E2E suite. Two lean images (Playwright + Python) give you reproducibility, isolation, and portability. The Harness pipeline orchestrates which image runs at each step. You get the best of both worlds: Playwright for what it's great at (UI), Python for what it's great at (everything else), and Docker to make it all reliable.
