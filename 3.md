GitHub Copilot Instructions for Spring Boot Microservices
1. Project overview
	•	This repository contains one or more Java microservices built with Spring Boot, exposing RESTful APIs in a distributed system.
	•	Each microservice is independently deployable and is aligned to a specific business domain or bounded context.
2. Tech stack and versions
	•	Language: Java 17+ (prefer latest LTS).
	•	Frameworks: Spring Boot (2.7+/3.x), Spring Web, Spring Data JPA, Spring Validation, Spring Security, Spring Cloud (Gateway, OpenFeign, Config, Circuit Breaker/Resilience4j where relevant).
	•	Data: Relational database (e.g., PostgreSQL/MySQL) via JPA/Hibernate; schema migrations with Flyway or Liquibase.
	•	Infrastructure: Docker containers; optional Kubernetes or Docker Compose for local orchestration.
3. Architecture and project structure
	•	Use layered architecture inside each microservice:
	•	 controller  (or  web ) layer for REST endpoints.
	•	 service  layer for business logic (thin controllers, no business logic in controllers).
	•	 repository  layer for persistence using Spring Data.
	•	 domain/model  for entities, value objects, and core domain types.
	•	 config  for Spring configuration, security, messaging, etc.
	•	Organize code per bounded context or feature where appropriate; avoid cross‑module coupling.
4. Coding and API design guidelines
	•	Follow REST best practices:
	•	Plural nouns for resources ( /api/users ,  /api/orders ).
	•	Use standard HTTP methods and status codes (GET for reads, POST for creation, PUT/PATCH for updates, DELETE for deletion).
	•	Use DTOs for request/response models; avoid exposing JPA entities directly over the wire.
	•	Prefer constructor injection, final fields, and immutability where reasonable; avoid field injection.
	•	Use Bean Validation ( @Valid ,  @NotNull , etc.) on incoming requests and provide meaningful validation messages.
	•	Implement global exception handling with  @ControllerAdvice  and standardized error responses.
5. Microservice interaction and resilience
	•	Prefer loose coupling between services; share contracts (API/DTO schemas), not databases.
	•	For synchronous calls, use HTTP/REST, optionally with OpenFeign clients for declarative HTTP.
	•	For asynchronous communication, use messaging (Kafka/RabbitMQ/etc.) with clear event contracts.
	•	Wrap inter‑service calls with timeouts, retries, and circuit breakers (e.g., Resilience4j), and handle fallbacks where appropriate.
6. Security and compliance
	•	All external APIs must be authenticated and authorized (e.g., OAuth2/OIDC with JWT, Spring Security resource server).
	•	Deny by default: endpoints are secured unless explicitly marked as public.
	•	Never log secrets, API keys, passwords, private tokens, or full PII; mask or omit sensitive fields from logs.
	•	Use HTTPS/TLS in all non‑local environments; assume the gateway or ingress terminates TLS if applicable.
7. Configuration and environments
	•	Use  application.yml  plus profile‑specific files ( application-dev.yml ,  application-prod.yml , etc.).
	•	All environment‑specific values (URLs, credentials, feature flags) must come from configuration or environment variables, not be hardcoded.
	•	Prefer Spring Cloud Config or similar centralized configuration where used; keep defaults safe and minimal for local development.
8. Logging, metrics, and observability
	•	Use structured logging (e.g., JSON logs or consistent patterns) with context such as correlation/request IDs.
	•	Add health and readiness endpoints via Spring Boot Actuator; ensure they are suitable for container orchestration probes.
	•	Expose basic metrics and tracing hooks (Micrometer, OpenTelemetry, etc.) when the project uses them; reuse existing configuration patterns.
9. Performance and reliability practices
	•	Use pagination or streaming for list endpoints; avoid returning unbounded result sets.
	•	Add caching for read‑heavy, safe-to-cache operations when it clearly improves performance; integrate with the project’s chosen cache.
	•	Be careful with N+1 queries; prefer fetch joins or appropriate query tuning in repositories.
10. Testing expectations
	•	Always generate tests alongside new logic:
	•	Unit tests for services, utilities, and domain logic.
	•	Integration or slice tests for controllers and repositories using Spring testing support.
	•	Use in‑memory databases (H2) or Testcontainers for repository/integration tests as per project standard.
	•	Aim for meaningful coverage; focus on business logic, contracts, and error paths, not just the happy path.
11. Project workflow and conventions
	•	Follow existing naming conventions, package layout, and patterns already present in the repository.
	•	Place new controllers, services, repositories, and tests in the same packages and modules as similar existing code.
	•	Respect existing build tooling and scripts (Maven/Gradle, Dockerfiles, Makefiles); integrate new tasks consistently.
12. How Copilot should behave
	•	Prefer:
	•	Reusing existing abstractions, helpers, and configurations rather than inventing new ones.
	•	Generating small, focused methods and classes with clear responsibilities.
	•	Adding or updating tests when modifying or adding endpoints, services, or critical logic.
	•	Avoid:
	•	Introducing new third‑party libraries unless explicitly requested.
	•	Bypassing layers (e.g., repositories called directly from controllers).
	•	Changing CI/CD, infrastructure, or security configuration unless explicitly asked.
13. Limitations and caution areas
	•	Do not modify database schemas, migration scripts, or security rules unless prompted to and enough context is provided.
	•	Treat legacy or complex modules as sensitive; prefer small, isolated changes and ensure tests are added or updated.
