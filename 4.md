1.	Project overview
	•	What the project does, key features, main users, and current status (MVP, production, etc.). 
	•	High‑level architecture and main components (e.g., “set of Spring Boot microservices with REST APIs and Kafka integration”). 
	2.	Tech stack and dependencies
	•	Languages, frameworks, major libraries, databases, and infrastructure tools (Docker, Kubernetes, CI/CD). 
	•	Any versions or constraints Copilot must assume (e.g., Java 17, Spring Boot 3, PostgreSQL). 
	3.	Project structure
	•	Important folders and what lives in each (e.g., /service-name, /api, /domain, /tests). 
	•	Where to put new code (new endpoints, new domain models, new tests). 
	4.	Code and design guidelines
	•	Coding style, patterns (DDD, hexagonal, layered), naming conventions, and architecture rules. 
	•	Rules about REST design, error handling, logging, and how to structure classes or functions. 
	5.	Testing expectations
	•	Required test types (unit, integration, e2e), frameworks, and coverage expectations. 
	•	Where tests should be created and any standard test patterns or fixtures to reuse. 
	6.	Security and compliance rules
	•	Authentication/authorization approach, sensitive data handling, and what must never be logged or generated. 
	•	Any regulatory, privacy, or internal policy constraints Copilot should respect. 
	7.	Workflow and tooling
	•	How to run, build, and test the project (key scripts/commands, Makefiles, package scripts). 
	•	How branches, commits, and pull requests should be formatted or validated. 
	8.	Preferred behaviors for Copilot
	•	What to always do (e.g., “always add tests for new endpoints,” “reuse existing patterns,” “ask before adding new dependencies”). 
	•	What to avoid (e.g., “do not bypass service layer,” “do not create global state,” “avoid heavy external libraries”). 
	9.	Limitations and known issues
	•	Things Copilot should not attempt (e.g., “don’t modify CI config without explicit request,” “don’t change database schema directly”). 
	•	Known tricky areas or legacy modules that require extra caution or human review. 
	10.	Examples and templates (optional but powerful)
	•	A few short examples of “good” code or responses that illustrate the style you want. 
	•	Example workflows (“when adding a new microservice endpoint, follow these steps: …”) as brief checklists.
